# X.509-SVID mTLS between two workloads

This guide shows the other half of SPIFFE identity. The quick start uses a
JWT-SVID to prove a workload to Akeyless. Here, two workloads use X.509-SVIDs
to prove who they are to each other over mutual TLS.

These are two different problems. A JWT-SVID is a bearer token you hand to a
service like Akeyless. An X.509-SVID is a certificate you use to open an
encrypted, mutually authenticated connection between two workloads. Akeyless
authenticates the workload with a JWT, so the JWT path stays as it is. This
demo is separate and needs only SPIRE; it does not touch Akeyless.

## When to use X.509 mTLS

Use it when two of your services call each other directly and you want that call
authenticated and encrypted without a shared secret. A `billing` service calls a
`payouts` service over HTTPS; both present X.509-SVIDs, and `payouts` accepts
only `billing`'s SPIFFE ID. The JWT path still handles Akeyless; X.509 handles
the call between services. Reach for this for service-to-service trust, not for
workload-to-Akeyless trust.

## What the demo does

Two small Go programs, `mtls/server` and `mtls/client`, run in the host
container. Each fetches its own X.509-SVID from the Workload API with
[go-spiffe](https://github.com/spiffe/go-spiffe), the canonical Go SPIFFE
library, which also refreshes the SVID and trust bundle automatically.

- The server presents its X.509-SVID and accepts connections only from the
  client's SPIFFE ID.
- The client presents its X.509-SVID and accepts the server only if it presents
  the server's SPIFFE ID.
- After the handshake, each side prints the identity of the other, proving the
  authentication worked in both directions.

## How the two workloads get distinct identities

Both programs run in the same host container, so they share one spire-agent.
SPIRE decides which identity to hand a caller by matching the caller's
selectors. The demo's main app is registered as `unix:uid:0`. If the mTLS
programs also ran as root, every root process would match the same selector,
and SPIRE could not tell them apart.

So each mTLS program runs as its own UID, and each is registered with that UID:

- The server runs as uid 10001, registered as
  `spiffe://example.org/ns/default/sa/mtls-server`.
- The client runs as uid 10002, registered as
  `spiffe://example.org/ns/default/sa/mtls-client`.

Distinct UIDs give each workload an unambiguous identity. This is the same
reason production narrows selectors to a dedicated UID per workload, described
in [Production hardening](05-production.md).

## Run it

Start SPIRE first, if you have not already:

```bash
./spire/up.sh
```

Then run the demo:

```bash
./mtls/run-mtls.sh
```

The script registers the two workloads against the running spire-server and
runs the mTLS exchange in the host container. It prints, on both sides, the
authenticated peer identity:

```
[mtls] starting mTLS server as uid 10001 ...
[mtls] waiting for the server to come up ...
[mtls] running mTLS client as uid 10002 ...
[client] my identity: spiffe://example.org/ns/default/sa/mtls-client
[client] authenticated server=spiffe://example.org/ns/default/sa/mtls-server
[client] server replied: hello from the spiffe://example.org/ns/default/sa/mtls-client server

[mtls] server log:
[server] my identity: spiffe://example.org/ns/default/sa/mtls-server
[server] listening on 127.0.0.1:8443, accepting only spiffe://example.org/ns/default/sa/mtls-client
[server] authenticated client=spiffe://example.org/ns/default/sa/mtls-client
```

The client proved the server's identity and the server proved the client's.
The reply line confirms the channel carries data after the handshake.

## See the authorization fail

The check is real, not cosmetic. If the client expects the wrong server
identity, the handshake is rejected. You can see this by running the in-container
demo with a wrong expected server ID:

```bash
docker compose --project-directory . -f spire/docker-compose.yml exec \
  -e MTLS_SERVER_SPIFFE_ID=spiffe://example.org/ns/default/sa/WRONG \
  -e MTLS_CLIENT_SPIFFE_ID=spiffe://example.org/ns/default/sa/mtls-client \
  -e MTLS_SERVER_UID=10001 -e MTLS_CLIENT_UID=10002 \
  host /app/mtls/demo.sh
```

The client aborts with `unexpected ID "spiffe://example.org/ns/default/sa/mtls-server"`
because the server presented its real identity, not the wrong one the client was
told to expect. The same rejection happens on the server side if the client
presents the wrong identity.

## Configuration

The workload identities derive from the trust domain, like every other SPIFFE
ID in this repo. Override them in `.env` if you want different names:

```
MTLS_SERVER_SPIFFE_ID=spiffe://<trust-domain>/ns/default/sa/mtls-server
MTLS_CLIENT_SPIFFE_ID=spiffe://<trust-domain>/ns/default/sa/mtls-client
```

The UIDs default to 10001 and 10002. Change `MTLS_SERVER_UID` and
`MTLS_CLIENT_UID` only if those UIDs are already in use on the host, and
remember the registration selectors in the server must match whatever UIDs you
choose.

The lifetime of these X.509-SVIDs is governed by `X509_SVID_TTL` in `.env`,
which defaults to SPIRE's one hour. See
[Configuration](04-configuration.md#lifetimes). The go-spiffe library refreshes
each SVID before it expires, so long-lived servers and clients keep working
across rotation without code changes.

## Files

- `mtls/server/main.go` and `mtls/client/main.go`: the go-spiffe mTLS pair.
- `mtls/demo.sh`: runs inside the host container, starting the server as its
  own child and tearing it down before exit so nothing lingers.
- `mtls/run-mtls.sh`: the host-side entry point that registers the workloads
  and invokes `demo.sh`.

## Why this is not used to authenticate to Akeyless

You might expect X.509-SVIDs to authenticate the workload to Akeyless too. They
do not, because of how Akeyless validates certificates. A SPIFFE X.509-SVID
carries its identity in the URI SAN of the certificate, with an empty Subject.
Akeyless's certificate auth method identifies a client by a Subject field such
as the common name, and trusts a static CA you upload at creation time. That
extracts the wrong field, and the static CA goes stale every time SPIRE rotates
its signing key. So the JWT path is the correct way to authenticate to Akeyless,
and X.509-SVIDs are for mTLS between workloads, which is what this demo shows.
